# GitHub Portfolio Audit

A structured, agent-assisted workflow for auditing, organizing, and improving a long-running GitHub portfolio.

This project is being used to review the repositories of [`fnalin`](https://github.com/fnalin) and transform years of accumulated projects, experiments, studies, and historical code into a clearer professional portfolio.

The process is designed around an important principle:

> AI agents analyze and recommend. Human decisions determine what changes.

## Goals

The audit aims to:

- inventory existing repositories;
- identify relevant technologies and project types;
- distinguish professional projects, studies, experiments, forks, and historical work;
- identify repositories worth deeper technical review;
- identify potential security or privacy concerns;
- find projects with modernization potential;
- select projects that best demonstrate current engineering experience;
- reduce unnecessary noise without erasing useful technical history;
- progressively improve repository documentation and presentation.

The final objective is a GitHub profile that more clearly represents an experienced **Senior Backend / .NET Software Engineer** while preserving relevant parts of the developer's technical history.

## Approach

The audit follows an incremental workflow rather than allowing an AI agent to autonomously reorganize the account.

```text
Repository Metadata
        │
        ▼
   01 — Inventory
        │
        ▼
    Human Review
        │
        ▼
     02 — Triage
        │
        ▼
 Repository Selection
        │
        ▼
   Deep Technical Review
        │
        ▼
 Portfolio Strategy
        │
        ▼
 Approved Improvements
```

Each stage is defined as an explicit task with its own inputs, constraints, deliverables, and acceptance criteria.

The next stage is not automatically executed.

## Human-in-the-Loop

Recommendations generated during the audit are advisory.

Repository deletion, archival, visibility changes, modernization, or other modifications require explicit human approval.

Decisions made during the process are recorded separately from automated analysis so that future agent sessions do not silently override previous decisions.

## Repository Structure

```text
.
├── CLAUDE.md
├── README.md
├── data/
├── docs/
│   └── decisions.md
├── reports/
├── repos/
├── scripts/
└── tasks/
    └── 01-inventory.md
```

### `CLAUDE.md`

Persistent instructions and safety constraints for Claude Code.

It defines **how the agent should work**, not what task it should execute.

### `tasks/`

Task specifications.

Each task defines:

- objective;
- inputs;
- outputs;
- instructions;
- constraints;
- acceptance criteria.

Tasks are executed individually and require review before progressing to subsequent stages.

### `data/`

Local raw data used as input for analysis.

Generated or account-specific data is intentionally excluded from version control when appropriate.

### `repos/`

Temporary local clones used for deeper source-code analysis.

Cloned repositories are excluded from this repository's Git history and are treated as read-only evidence during audit phases.

### `reports/`

Results generated by audit tasks.

Reports distinguish factual observations from interpretations and recommendations.

### `docs/`

Human-maintained project documentation.

`docs/decisions.md` records decisions made during the audit. Human decisions take precedence over automated recommendations.

### `scripts/`

Utilities that make the audit process more reproducible, such as repository metadata collection and analysis helpers.

## Agent Instructions vs. Tasks

The project deliberately separates permanent agent instructions from individual work items.

```text
CLAUDE.md
    │
    └── HOW the agent must operate

tasks/
    │
    └── WHAT should be done

reports/
    │
    └── WHAT was discovered

docs/decisions.md
    │
    └── WHAT the human decided
```

This keeps agent behavior consistent while allowing the audit workflow to evolve incrementally.

## Safety

The audit defaults to read-only operations.

Without explicit authorization, the agent must not:

- delete or archive repositories;
- change repository visibility;
- rename repositories;
- modify GitHub settings;
- push changes to analyzed repositories;
- create or delete remote branches;
- modify the GitHub profile.

Potential secrets or sensitive information discovered during analysis must never be reproduced in reports.

## Technology Focus

While the audit covers the complete repository history, particular attention is given to projects related to:

- C# / .NET;
- ASP.NET Core;
- backend architecture;
- REST APIs;
- distributed systems;
- databases;
- Docker;
- authentication and authorization;
- automated testing;
- CI/CD;
- cloud;
- observability;
- AI / LLM integration.

Older technologies are not automatically considered irrelevant. Historical projects may provide useful evidence of experience and technical evolution.
