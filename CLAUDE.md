# Workspace Structure

## `data/`

Raw data used as input for analysis.

Treat source data as read-only unless a task explicitly states otherwise.

## `tasks/`

Contains task specifications.

Tasks define WHAT must be done.

Execute only the task explicitly requested by the user.

Do not automatically proceed to the next task.

## `reports/`

Contains outputs generated by audit tasks.

Reports must clearly distinguish facts from recommendations.

## `repos/`

Local workspace for repositories cloned for deeper analysis.

Repositories inside this directory are considered read-only during audit activities unless the user explicitly authorizes modifications.

Never include cloned repositories in this repository's Git history.

## `scripts/`

Contains utilities developed specifically to support this audit.

Scripts must default to read-only behavior toward GitHub.

## `docs/`

Contains project documentation and human decisions.

`docs/decisions.md` records decisions made by the portfolio owner.

These decisions take precedence over automated recommendations.

# Task Execution Rules

Before starting work:

1. Read this file.
2. Read the requested task completely.
3. Identify its inputs, outputs, constraints, and acceptance criteria.
4. Execute only that task.
5. Validate its acceptance criteria.
6. Stop after completing the task.

Never automatically start another task.

If the task conflicts with this file, follow this file and report the conflict.

If required information is missing, do not invent it.

Record uncertainty explicitly.

---

# GitHub Safety Rules

Read-only GitHub operations are allowed.

Local cloning into `repos/` is allowed only when required by the active task.

Unless explicitly authorized by the user, NEVER:

- delete repositories;
- archive repositories;
- change repository visibility;
- rename repositories;
- modify repository settings;
- push commits;
- force push;
- create or delete remote branches;
- create releases;
- change repository descriptions;
- change repository topics;
- modify the GitHub profile;
- modify GitHub Actions remotely.

Do not interpret a recommendation as authorization to execute it.

---

# Source Repository Protection

Repositories cloned into `repos/` are evidence used by the audit.

During analysis, do not:

- refactor source code;
- upgrade dependencies;
- format source files;
- fix bugs;
- rewrite documentation;
- modify configuration;
- commit changes.

Inspection commands and local builds/tests are allowed only when required by the active task and when they do not modify tracked source files.

# Security and Privacy

While analyzing repositories, watch for potential:

- passwords;
- API keys;
- access tokens;
- credentials;
- private keys;
- certificates;
- sensitive connection strings;
- personal information;
- confidential corporate information;
- proprietary source code that may not be appropriate for a public repository.

Never reproduce secret values in reports, terminal summaries, or documentation.

Use `[REDACTED]` when necessary.

Report only:

- repository;
- file;
- approximate location;
- category of exposure;
- recommended remediation.

# Analysis Principles

Do not assume old code is bad code.

This GitHub account represents many years of software development.

Evaluate repositories based on evidence, including:

- technical substance;
- architecture;
- complexity;
- originality;
- code quality;
- professional relevance;
- documentation;
- automated tests;
- maintainability;
- security;
- modernization potential;
- portfolio value.

Do not favor a repository merely because it is newer.

Do not penalize a repository merely because its technology is old.

Distinguish between:

- metadata-based observations;
- source-code-based observations;
- assumptions;
- recommendations.

When only metadata has been inspected, explicitly describe conclusions as preliminary.

# Repository Classification

When classification is requested by a task, use:

- `SHOWCASE`
- `REVITALIZE`
- `STUDY`
- `HISTORICAL`
- `ARCHIVE_CANDIDATE`
- `PRIVATE_OR_DELETE_CANDIDATE`
- `REVIEW_MANUALLY`

When uncertain, prefer `REVIEW_MANUALLY`.

A classification is a recommendation, never an instruction to change the repository.

---

# Portfolio Value

When portfolio value is requested, use:

- `HIGH`
- `MEDIUM`
- `LOW`
- `UNKNOWN`

Do not use numeric scores.

---

# Evidence Standard

Recommendations must cite concrete evidence whenever possible.

Examples:

- repository metadata;
- `.sln` and project files;
- framework versions;
- source organization;
- architecture;
- tests;
- Docker configuration;
- CI/CD configuration;
- documentation;
- dependencies;
- commit history.

Do not infer source-code quality from repository name or description alone.

# Human Decisions

Automated analysis is advisory.

The portfolio owner makes all final decisions.

Before recommending an action, check `docs/decisions.md` for an existing human decision concerning that repository.
