# Workspace Structure

## `data/`

Raw data used as input for analysis.

Treat source data as read-only unless a task explicitly states otherwise.

Generated or account-specific raw data may be excluded from version control.

## `tasks/`

Contains task specifications.

Tasks define WHAT must be done.

Execute only the task explicitly requested by the user.

Do not automatically proceed to the next task.

Contains outputs generated by audit tasks.

Reports must clearly distinguish facts from interpretations and recommendations.

Local workspace for repositories cloned for deeper analysis.

# Instruction Hierarchy

This file defines the persistent operating rules for agents working in this repository.

Task specifications define individual units of work.

If a task conflicts with this file, follow this file and report the conflict.

A task may further restrict these instructions, but it must not relax safety constraints defined in this file unless the user explicitly authorizes the specific action.

User authorization for a specific action does not imply authorization for unrelated actions.

If required information is missing, do not invent it.

Record uncertainty explicitly.

---

# Task Execution Rules

Before starting work:

1. Read this file.
2. Read the requested task completely.
3. Verify that the task is eligible for execution based on its status.
4. Identify its inputs, outputs, constraints, and acceptance criteria.
5. Execute only that task.
6. Validate its acceptance criteria.
7. Stop after completing the task.

Never automatically start another task.

Do not create new task specifications unless explicitly requested.

Completing a task may include recommending a possible next task, but the agent must not create or execute it automatically.

If a task cannot be completed because required information, access, or a human decision is missing, stop and report the blocking condition.

---

# Task Status

Tasks may use the following statuses:

- `DRAFT` — being designed and not ready for execution;
- `READY` — reviewed and available for execution;
- `IN_PROGRESS` — currently being executed;
- `BLOCKED` — cannot continue without additional information or a human decision;
- `COMPLETED` — acceptance criteria have been satisfied.

The agent must not execute a task marked `DRAFT`.

A task marked `BLOCKED` must not be resumed until the blocking condition has been resolved.

Task status changes must reflect actual execution state and must not be used to imply human approval.

Completing a task does not authorize execution of another task.

# GitHub Safety Rules

Read-only GitHub operations are allowed.

Local cloning into `repos/` is allowed only when required by the active task.

Unless explicitly authorized by the user, NEVER:

- delete repositories;
- archive repositories;
- change repository visibility;
- rename repositories;
- modify repository settings;
- push commits;
- force push;
- create or delete remote branches;
- create releases;
- change repository descriptions;
- change repository topics;
- modify the GitHub profile;
- modify GitHub Actions remotely.

Do not interpret a recommendation as authorization to execute it.

Authorization must be specific to the requested operation.

# Audit Repository vs. Analyzed Repositories

This repository (`github-portfolio-audit`) and repositories under `repos/` have different roles.

The audit repository contains:

- agent instructions;
- task specifications;
- reports;
- scripts;
- audit documentation.

Repositories under `repos/` are external projects being analyzed.

Authorization to modify, commit, or push changes in this audit repository does NOT grant permission to modify, commit, or push changes in repositories under `repos/`.

Authorization for an analyzed repository must be explicit and repository-specific.

Never propagate permissions from this repository to an analyzed repository.

# Source Repository Protection

Repositories cloned into `repos/` are evidence used by the audit.

During analysis, do not:

- refactor source code;
- upgrade dependencies;
- format source files;
- fix bugs;
- rewrite documentation;
- modify configuration;
- commit changes.

Inspection commands are allowed when required by the active task.

Local builds and tests are allowed only when required by the active task and when they do not intentionally modify tracked source files.

If a build, test, or inspection command unexpectedly modifies tracked files, stop and report the change.

Do not commit or discard unexpected modifications without explicit authorization.

# Analysis Principles

Do not assume old code is bad code.

This GitHub account represents many years of software development.

Evaluate repositories based on evidence, including:

- technical substance;
- architecture;
- complexity;
- originality;
- code quality;
- professional relevance;
- documentation;
- automated tests;
- maintainability;
- security;
- modernization potential;
- portfolio value.

Do not favor a repository merely because it is newer.

Do not penalize a repository merely because its technology is old.

Distinguish between:

- metadata-based observations;
- source-code-based observations;
- assumptions;
- recommendations.

When only metadata has been inspected, explicitly describe conclusions as preliminary.

Do not present assumptions as facts.

# Repository Classification

When classification is requested by a task, use one primary classification:

- `SHOWCASE`
- `REVITALIZE`
- `STUDY`
- `HISTORICAL`
- `ARCHIVE_CANDIDATE`
- `PRIVATE_OR_DELETE_CANDIDATE`
- `REVIEW_MANUALLY`

When uncertain, prefer `REVIEW_MANUALLY`.

A classification is a recommendation, never an instruction to change the repository.

Classification must be supported by the level of evidence available.

Metadata-only analysis must not be presented as a final source-code assessment.

---

# Portfolio Value

When portfolio value is requested, use:

- `HIGH`
- `MEDIUM`
- `LOW`
- `UNKNOWN`

Do not use numeric scores.

Portfolio value and repository classification are separate concepts.

For example, a historical repository may have low relevance to the current technology focus while still being worth preserving.

# Evidence Standard

Recommendations must cite concrete evidence whenever possible.

Examples include:

- repository metadata;
- `.sln` and project files;
- framework versions;
- source organization;
- architecture;
- tests;
- Docker configuration;
- CI/CD configuration;
- documentation;
- dependencies;
- commit history.

Do not infer source-code quality from repository name or description alone.

Clearly state the evidence level behind significant recommendations.

When evidence is insufficient, use `UNKNOWN`, `REVIEW_MANUALLY`, or explicitly request deeper analysis rather than guessing.

# Git Conventions

Use Conventional Commits when commit creation is explicitly authorized.

Preferred types include:

- `feat:` — new project capability or workflow;
- `fix:` — correction of incorrect behavior;
- `docs:` — documentation-only changes;
- `refactor:` — structural changes without changing behavior;
- `test:` — tests;
- `build:` — build system or dependency changes;
- `ci:` — CI/CD changes;
- `chore:` — maintenance and tooling changes.

Examples:

`feat: add repository inventory workflow`

`docs: document portfolio audit methodology`

`fix: handle duplicate repository metadata`

`chore: update gitignore rules`

Keep commit messages concise, imperative, and descriptive.

Do not create commits or push changes unless explicitly authorized by the user.

Authorization to commit or push changes in this audit repository does not grant permission to commit or push changes in repositories under `repos/`.

Authorization for analyzed repositories must be explicit and repository-specific.

---

# Human Decisions

Automated analysis is advisory.

The portfolio owner makes all final decisions.

Before recommending an action for a repository, check `docs/decisions.md` for an existing human decision concerning that repository.

Never silently override a recorded human decision.

If new evidence conflicts with an existing human decision:

1. preserve the existing decision;
2. report the new evidence;
3. explain the conflict;
4. request human review when appropriate.

Reports may reference human decisions but must not modify `docs/decisions.md` unless the active task explicitly requires recording a decision approved by the user.

An agent recommendation must never be recorded as a human decision.

# Operating Principle

The default behavior of this project is:

**inspect → document → recommend → human review → explicitly authorized action**

Never collapse recommendation and execution into the same step unless the user has explicitly authorized that specific action.
