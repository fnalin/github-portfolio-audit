# Task 01 — Repository Inventory

## Status

COMPLETED

## Objective

Create a complete and factual inventory of the public GitHub repositories belonging to `fnalin`.

This task analyzes repository metadata only.

Its purpose is to establish a reliable overview of the portfolio before repository classification or source-code analysis begins.

Do not inspect repository source code during this task.

---

## Input

Use the canonical metadata dataset generated by Task 00:

`data/repositories.json`

Treat this file as read-only.

Do not use the legacy files:

- `data/github-repos-1.json`
- `data/github-repos-2.json`

They are retained locally only as historical validation data.

---

## Preconditions

Before proceeding:

1. verify that `data/repositories.json` exists;
2. verify that it contains valid JSON;
3. verify that its root value is an array;
4. verify that repository IDs are unique;
5. verify that repository names are unique.

If any precondition fails, mark the task as `BLOCKED`, report the reason, and stop.

Do not regenerate metadata automatically.

Task 00 owns metadata collection.

---

## Output

Create:

`reports/01-inventory.md`

The report is a version-controlled audit artifact.

Do not create additional reports during this task.

---

## Repository Inventory

Every repository in `data/repositories.json` must appear exactly once in the inventory.

For each repository, extract the following metadata when available:

- repository name;
- description;
- GitHub URL;
- creation date;
- last update date;
- last push date;
- primary language;
- fork status;
- archived status;
- disabled status;
- visibility;
- default branch;
- stars;
- forks;
- open issues;
- repository size;
- license;
- topics.

Do not invent missing values.

Represent unavailable information consistently as `UNKNOWN`, `NONE`, or another clearly documented value.

---

## Portfolio-Level Statistics

Calculate useful factual statistics for the complete portfolio.

Include at least:

- total repository count;
- original repository count;
- fork count;
- archived repository count;
- disabled repository count;
- repositories with and without descriptions;
- repositories with and without detected primary languages;
- repositories with and without licenses;
- repositories by primary language;
- repository creation by year;
- repository last-push activity by year.

When useful, also identify:

- oldest repositories;
- most recently created repositories;
- most recently pushed repositories;
- repositories with the most stars;
- repositories with the most forks.

These are factual observations only.

Do not treat stars, forks, or recency as measures of code quality.

---

## Preliminary Metadata Observations

After the factual inventory, provide a limited metadata-only analysis.

Identify repositories that may deserve deeper investigation based on observable signals such as:

- relevance to C#, .NET, backend development, databases, architecture, cloud, Docker, distributed systems, or AI;
- repository descriptions suggesting substantial original projects;
- unusual technical scope;
- meaningful historical age;
- recent development activity;
- significant repository size;
- notable community activity;
- repository naming suggesting courses, samples, experiments, exercises, or tutorials;
- fork status.

These observations are intended to guide the next audit phase.

They are NOT final repository classifications.

---

## Potential Deep-Review Candidates

Identify a manageable set of repositories that appear to justify deeper investigation.

For each candidate, explain:

- why it was selected;
- which metadata supports the selection;
- what should be investigated during source-code review.

Do not assign final portfolio classifications such as `SHOWCASE`, `REVITALIZE`, or `ARCHIVE_CANDIDATE` during this task.

Do not assign portfolio value (`HIGH`, `MEDIUM`, `LOW`) during this task.

Those decisions require stronger evidence.

---

## Potential Low-Priority Repositories

Identify repositories that may not require immediate deep analysis based on clear metadata signals such as:

- forks;
- obvious exercises;
- course repositories;
- tutorial copies;
- minimal experiments;
- empty or nearly empty repositories.

This section establishes review priority only.

Do not recommend deletion, archival, or visibility changes based solely on metadata.

---

## Data Quality

Document any metadata issues discovered, including:

- missing descriptions;
- missing languages;
- missing licenses;
- unusual or inconsistent dates;
- unexpected visibility;
- duplicate-looking repository names;
- suspicious metadata inconsistencies;
- fields that cannot be reliably interpreted.

Do not attempt to repair metadata.

---

## Report Structure

`reports/01-inventory.md` must contain the following sections:

### 1. Executive Summary

A concise overview of the public GitHub portfolio based entirely on metadata.

### 2. Portfolio Statistics

Factual aggregate statistics and distributions.

### 3. Repository Inventory

A complete table containing every repository exactly once.

Keep the table useful and readable. If some metadata is better represented in supporting subsections rather than making the table excessively wide, use reasonable judgment.

### 4. Technology and Activity Overview

Summarize language distribution, repository age, and activity patterns.

Do not infer technical proficiency solely from repository counts.

### 5. Potential Deep-Review Candidates

Repositories that appear worth investigating in a later task.

### 6. Potential Low-Priority Repositories

Repositories that appear less urgent for source-code review.

### 7. Data Quality and Limitations

Missing metadata, ambiguity, and limitations of metadata-only analysis.

### 8. Proposed Next Step

Recommend what the next audit task should investigate.

Do not create or execute that task.
